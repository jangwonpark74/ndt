# Samsung CongitV NDT · Regional 3D viewer

A regional viewer combining MapLibre GL JS, Three.js and OpenStreetMap-derived vector tiles. Choose Toronto or New York City with the Region buttons in the left sidebar. The viewer loads map and elevation tiles as you move around either region and beyond; it does not use F4 Map assets or endpoints.

The project identifier is `toronto-ndt`. This directory contains the viewer, its data preparation scripts and its tests.

## Run locally

Run the following commands from the workspace root, one directory above `ndt/`. Install [uv](https://docs.astral.sh/uv/getting-started/installation/) and GNU Make. uv manages a local Python environment (the project's current Python requirement is in the root `pyproject.toml`); the viewer has no Python package dependencies. The map and terrain tile services require an internet connection.

```sh
make setup
make run
```

`make setup` runs `uv sync --locked`; `make run` uses `uv run --locked` and creates the environment automatically if needed. It tries ports 5179–5189 and prints the actual URL; stop the server with Ctrl+C. To use an exact port, run `make run PORT=5180`; if it is occupied, the command reports the conflict. The server binds to the local machine by default; `HOST` can be overridden when network access is intended. The Makefile uses `.cache/uv` by default; override `UV_CACHE_DIR` if preferred. The Python server stores data in `regions.sqlite3` in the project root and refreshes changed regional assets on restart. If the root database does not exist, the server copies the previous `ndt/var/regions.sqlite3` database on first startup. Stop all older viewer instances before starting the updated server, so no edits are made to the old database after the copy. The old database is retained; an existing root database is never overwritten. Asset tables can be regenerated from source files, but project site edits are saved only in the database; keep or back it up to preserve them. To choose another database explicitly, run `uv run --locked python ndt/server.py --db /path/to/database.sqlite3`. A static HTTP server alone does not provide the required SQLite API.

The region catalog is in `regions.json`, with region-specific centers and project shortcuts. Toronto's assets are under `dist/`; New York's are under `data/new-york/`. The SQLite `regions` and `region_assets` tables isolate each region. A new region needs a catalog entry, regional roof/tree/street datasets in the same formats, and an appropriate network-data adapter; network sources are not interchangeable between jurisdictions.

Each Toronto network site and New York reservation is also stored individually in `network_sites`, keyed by region, dataset path and site ID. Its `feature` JSON retains all original properties and geometry; `longitude` and `latitude` are indexed generated columns. `network_datasets` retains the collection metadata and the server builds network GeoJSON responses from these rows. `region_assets` keeps the imported source snapshot. Existing databases are upgraded from their stored snapshots on startup when the source fingerprint is unchanged, preserving project assignments. With unchanged source files, site rows survive restarts. When any regional source asset changes, the server reimports that region's network records from the source files; back up the database before refreshing if its records have been changed. Import failure rolls the refresh back. Site editing and audit history are not provided by the viewer.

For example, inspect the stored site and reservation counts with:

```sql
SELECT region_id, dataset_path, COUNT(*) AS locations
FROM network_sites
GROUP BY region_id, dataset_path;
```

New York records are NYC pole reservations associated with Verizon, not a verified inventory of operating radio sites.

If you moved or renamed the project and use the virtual environment's activation scripts, recreate the environment with `uv venv --clear` followed by `make setup`; activation scripts contain absolute paths.

Drag to pan, right-drag to rotate, and scroll to zoom. The camera controls also provide zoom, tilt, rotation, a north reset and a Home button that returns to the city overview; the separate Region overview menu item is removed. Camera controls can be used with a keyboard or touch. Use the Region buttons and Project dropdown in the left sidebar to navigate, or submit a location search in the header and choose a result. Search sends the query and current map center to the [Photon public demo service](https://github.com/komoot/photon#demo-server), which may be unavailable or rate-limited; it uses OpenStreetMap data. Click a visible feature to mark it on the map. Open Map Settings in the sidebar to toggle buildings, streets, trees, terrain and street details independently. The illustrative light comes from the southeast; optional building shadows project away from it and are off by default. MapLibre GL JS and Three.js are bundled; fonts load from Google Fonts when available.

In Toronto, the Network sidebar shows ISED-reported sites on the OSM map. **TELUS sites** are teal for indoor, purple for outdoor and grey for mixed, underground or unspecified locations. **Bell outdoor** locations are orange and can be switched independently. Indoor sites remain visible; outdoor markers are shown when the overview has a usable fan. The site search still includes other licensed records. Bell sites are shown as shared-network context; TELUS use of a particular Bell site is not established by the ISED licence alone. Select a marker or nearby item for the licensee, record count, reported technologies, site type and antenna height. Records at identical coordinates share one marker per licensee.

Select a location to see its reported site description, coordinates and available ISED site identifiers. Expand **Cell and antenna records** for TELUS or **Reported directional bearings** for Bell to inspect the published radio attributes. A ring indicates that all TELUS records at that location are non-directional. At zoom 14 and closer, arrows point along the distinct reported directional TX azimuths for TELUS or Bell. At all zoom levels, Bell outdoor locations with exactly three bearings and valid beamwidths automatically display colored planning fans for bearings with usable frequencies; toggle **Sector fans** to hide them. Selecting a site is optional and shows its individual radius estimates. Each fan uses the widest reported beamwidth for its bearing, enlarged to at least 15° for visibility. Colors indicate bearing order, not a cell ID or technology. The 783 TELUS records in this extract are non-directional; 865 Bell outdoor coordinate pairs have valid directional bearings, including 454 with exactly three. A bearing can group several radio records and does not by itself establish a unique physical sector.

Selecting a Bell site highlights every bearing with a usable reported direction, beamwidth and frequency, even at locations with a number of bearings other than three; bearing colors repeat after three. Click a fan to emphasize it and show its bearing, frequency, reported and displayed beamwidth, and calculated and displayed radius. For overlapping fans, select a site and use its bearing buttons to choose a sector; these buttons are also keyboard accessible. TELUS non-directional records do not have sector fans.

Use **Find a licensed site** to search enabled TELUS and Bell records locally by reported location, site or cell ID, coordinates, or licensee. Search results show up to eight nearest matches. Select a result for its details and **View site in 3D**. The selected site has a map ring; **Show fans for selected site only** reduces overlap, and **Fan intensity** changes fill transparency without changing the calculation or the 5/12 display scale.

Each fan radius is an illustrative link-budget estimate using the urban macro (UMa) mean path-loss equations in [3GPP TR 38.901 v18.0.0, table 7.4.1-1](https://www.etsi.org/deliver/etsi_tr/138900_138999/138901/18.00.00_60/tr_138901v180000p.pdf), with the lowest reported TX frequency at each bearing. For visualization only, each fan is intentionally drawn at 5/12 of its original calculated radius to reduce clutter; the model estimate is unchanged, and selected-site details show both distances. The controls default to NLOS, an assumed 46 dBm EIRP and a −100 dBm received-power threshold; those values are planning assumptions, not published site parameters or 3GPP requirements. The calculation assumes a 25 m base station, 1.5 m receiver, 0 dBi receiver gain and no additional losses; it is limited to 10 m–5 km and 0.5–100 GHz. The scaled boresight radius is applied uniformly across the fan. There is no site-specific building or terrain modelling, shadow or fading margin, interference, load, penetration or directional antenna-pattern loss. It is neither measured coverage nor an RSRP/SINR or calibrated network prediction.

All four Toronto project boundaries appear when the region loads. Each cluster anchors at the nearest Bell location with three usable sector estimates, then selects the six closest eligible locations to that anchor. Selecting a project fits its boundary in the map and opens the task editor. The separate full-page Project Overview lists sites, their count, cluster radius, planning notes and saved tasks. The right-side popup has Tasks and Network switches and one close button; switching or closing it preserves the project and map layers. Use the active-project shortcut to open Project Overview. On a phone, navigation closes and the panel scrolls within a limited height so the map and controls remain usable. The selection imposes no fixed distance limit, so the displayed radius should be reviewed when source data changes. Each project boundary is the convex hull enclosing the selected locations' sectors, using full calculated radii and reported beamwidths without the overview fan's 5/12 radius scaling or minimum display width. The boundary is a single project area and may include gaps between sectors; it is not a coverage map. Changing the link-budget controls recalculates the boundaries for the same sites; if any estimate is unavailable, the affected boundary is hidden. The estimate is not measured coverage or confirmation of TELUS use. New York project boundaries are unavailable because its reservation records do not report the radio attributes required by the model.

To edit a Toronto project, select it and right-click a Bell location on the map, then choose **Add site to project** or **Remove site from project**. Added sites need three usable sector estimates. The boundary follows the current site list, and Project Overview warns when it contains other than the seven sites required for simulation. Edits are saved in the viewer's SQLite database and survive a restart. If saved site IDs disappear from a refreshed dataset, editing and the boundary for that project are unavailable rather than silently dropping sites. New York reservations cannot be used as coverage sites because their radio attributes are unavailable.

## Data and limitations

### New York City

- The selected operator is Verizon. The [NYC pole reservation dataset](https://data.cityofnewyork.us/City-Government/Mobile-Telecommunications-Franchise-Pole-Reservati/tbgj-tdd6) was downloaded on 2026-11-07 and filtered to franchisee `NY SMSA`. The [city's franchise agreement](https://www.nyc.gov/assets/oti/downloads/pdf/mobile-telecom-franchises/new-york-smsa-limited-partnership-mtf-agreement-2020.pdf) identifies Verizon Communications as its ultimate indirect owner. The snapshot has 701 reservations: 125 installed, 386 approved and 190 proposed. Proposed reservations are hidden on the map but remain available in the list and search. These are pole reservations, not a complete Verizon site inventory; they exclude locations held by other franchisees, including potentially Verizon-serving shared infrastructure. A reservation or installed status does not prove current live service. The source supplies no antenna bearing, beamwidth or frequency, so New York has no sector fans, coverage prediction, or claimed indoor-site inventory.
- New York OSM roofs, trees, and street details use the [BBBike NewYork extract](https://download.bbbike.org/osm/bbbike/NewYork/) dated 2026-10-31 (PBF SHA-256 `df25e4eebf77de05ff6c0517285feab5b1ee963ed8ff6a82c33864cb94bfbaee`). It contains 14,768 mapped roofs, 72,374 mapped trees, 6,074 estimated row trees, 17,287 lamps and 21,834 benches. These counts refer to the BBBike extract, which extends beyond the five boroughs and is not clipped to the city boundary; OSM completeness varies. Roof IDs follow the same provider-dependent matching as Toronto and have not been independently verified against New York tiles.
- The downloaded NYC JSON had 10,347 total records (all franchisees) and SHA-256 `f6bda705a42452824766253aae6a5bff65ac8c2ff40a099a261e6b378332c190`. To rebuild the Verizon snapshot from the NYC JSON download, run `python3 ndt/scripts/extract_nyc_verizon.py INPUT.json ndt/data/new-york/verizon-poles.geojson`. Rebuild OSM details with the existing extraction scripts, an empty output directory for each tiled layer, and the relevant source and checksum. Do not treat proposed or approved reservations as installed equipment.

### Toronto

- TELUS locations use 783 records at 60 distinct coordinate pairs, filtered from the [ISED Terrestrial Spectrum Licence Site Data Extract](https://ised-isde.canada.ca/site/spectrum-management-system/en/spectrum-management-system-data/download-sms-data) dated 2026-11-03. The approximate Toronto-area bounding box is longitude -79.64 to -79.10 and latitude 43.58 to 43.85; it is not a municipal boundary. Counts are records and coordinate pairs, not verified physical sites or towers. All records in this selection are classified as indoor (`site_type=I`, `structure_type=O`); their structure-height field is not applicable as a tower height under [ISED's field definition](https://ised-isde.canada.ca/site/spectrum-management-system/en/spectrum-management-system-data/text-format-spectrum-licence-site-data-upload). The viewer therefore shows location markers and reported TX antenna heights, but no 3D tower for these records. Reported LTE, 5GNR and HSPA are ISED attributes, not measured coverage or confirmation of current service.
- Bell outdoor context contains 174,416 records at 1,481 coordinate pairs in the same bounding box and ISED extract, filtered to licensee `Bell Mobility Inc.` and `site_type=O`. Records are summarized by attributes at each coordinate. This includes rooftop, pole, tower and other outdoor structures; an orange marker does not verify TELUS service at that particular location. The [CRTC describes Bell and TELUS's shared radio access network](https://crtc.gc.ca/eng/archive/2025/2025-245.htm), but the licence extract does not establish the service relationship for individual sites. Location pairs and reported heights are not independently surveyed or confirmed current.
- For an outdoor, purpose-built tower (`site_type=O`, `structure_type=T`), a schematic lattice model appears at zoom 14 or closer only when all records at that coordinate have the same valid 1–600 m ISED structure height. In this snapshot 140 Bell coordinate pairs meet that strict rule. Rooftops, mixed structures and records with missing or conflicting heights remain map markers. Model shape is illustrative, its height is as reported rather than independently surveyed, and its base uses terrain elevation. The planning model uses its stated fixed base-station height rather than these reported structure heights.
- Rebuild with `python3 scripts/extract_telus_sites.py Site_Data_Extract_FX.zip dist/telus-sites.geojson --ised-date 2026-11-03` and `python3 scripts/extract_bell_outdoor.py Site_Data_Extract_FX.zip dist/bell-outdoor-sites.geojson --ised-date 2026-11-03`. The ISED ZIP used here has SHA-256 `b9a81941b0d13d821d2cd4242876204d5410f41cc4da20ebfc0ed715b307c0f3`; verify a new extract's date and checksum before rebuilding. The previous strict 30 m OSM proximity comparison yielded zero matches; ISED coordinates are displayed directly and do not imply an OSM match. The OSM PBF checksum is listed below.

- [OpenFreeMap](https://openfreemap.org/) provides on-demand OpenMapTiles vector tiles based on OpenStreetMap, including roads, transit, water, land use, labels, points of interest and building footprints where present in its schema and style. The map is not limited to the original downtown snapshot. OSM data © OpenStreetMap contributors, available under the [ODbL](https://www.openstreetmap.org/copyright); attribution is displayed on the map.
- OpenFreeMap's vector tile schema and style select, transform and generalize OSM features and attributes by zoom. They do not expose every OSM tag or feature.
- [Mapterhorn](https://mapterhorn.com/attribution) provides Terrarium-encoded digital elevation tiles. MapLibre drapes the base map over this terrain with 1× vertical exaggeration. Elevations are sampled terrain estimates, not surveyed ground or building heights; coverage, resolution and accuracy depend on the source dataset.
- At zoom 15 and closer, mapped roof shapes replace matching flat tile extrusions using Three.js; mapped flat roof colours are overlaid where available. Roofs use OSM height, direction, orientation and colour tags when present, with estimated roof heights when absent. The original building and roof colors and material palette are preserved, except pure red is displayed as muted warm stone; the underlying source tags remain unchanged. The renderer supports gabled, skillion, hipped, pyramidal, dome, cone and onion shapes, including `pitched` and `shed` aliases; concave gabled and skillion footprints are supported. Flat and skillion roofs can preserve courtyards in mapped multipolygon relations. Other unsupported or invalid footprints and roof types fall back to the original flat extrusion. Matching uses ID suffixes observed in a Toronto tile and depends on the provider retaining compatible IDs. The Three.js layer also marks the selected feature.
- Trees come from the same BBBike Toronto extract: 54,879 `natural=tree` nodes and 5,113 estimated positions along mapped `natural=tree_row` ways. At overview zooms only unclustered tree points are shown; at zoom 15 and closer, individual trees are rendered in 3D using the elevation tiles. Row spacing defaults to 8 m when absent, and missing heights and crown sizes use illustrative defaults. These are not a tree census. From `ndt/`, rebuild the tree tiles with `uv run scripts/extract_trees.py Toronto.osm.pbf NEW_EMPTY_DIRECTORY --source "BBBike Toronto OSM extract 2026-10-31"` and place the resulting files in `dist/trees/`.
- At zoom 17 and closer, mapped `highway=street_lamp` and `amenity=bench` nodes from the same extract appear as simple terrain-aligned models. The extract has 29,015 lamps and 10,759 benches; the viewer shows at most 1,000 within 1.2 km of the map center. Model dimensions and bench orientation are illustrative, and a mapped point does not guarantee the feature still exists. From `ndt/`, rebuild with `uv run scripts/extract_street_detail.py Toronto.osm.pbf NEW_EMPTY_DIRECTORY --source "BBBike Toronto OSM extract 2026-10-31"` and place the resulting files in `dist/street-detail/`.
- Water color and fixed southeast lighting are visual treatments, not measured water conditions or sun position. Optional ground-draped building shadows approximate projected footprints, are limited to 1,500 polygons and cap building heights at 150 m. They do not account for terrain occlusion, building-to-building shadows, tree shadows, courtyards, or time of day; tile clipping and incomplete data may produce artifacts.
- Roof data is a fixed [BBBike Toronto OSM extract](https://download.bbbike.org/osm/bbbike/Toronto/) dated 2026-10-31; its PBF SHA-256 is `b8dc99b3b43de1542662c1479b8c567b121dbfc3207a1cd86be9786a323a1a81`. From `ndt/`, rebuild the roof subset from a downloaded PBF with `uv run scripts/extract_roofs.py Toronto.osm.pbf dist/toronto-roofs.json --source "BBBike Toronto OSM extract 2026-10-31"`. The extraction script installs its pinned osmium dependency into uv's cache; the application itself has no Python dependency.
- The application requires the external tile services at runtime. If map tiles are unavailable, the map cannot be used; if elevation tiles are unavailable, terrain is not verified. `dist/toronto.json` and `scripts/convert_osm.py` retain the earlier downtown snapshot and converter for reference, but the city-wide map does not use that snapshot.
- Three.js and OrbitControls are distributed under their included MIT license (`dist/vendor/LICENSE`); MapLibre GL JS uses the included BSD license (`dist/vendor/MAPLIBRE-LICENSE.txt`).

## Check

Node.js is needed for the JavaScript tests and syntax checks. Run `make test` for the OSM parsing, tile attributes, tree extraction and roof geometry tests, or `make check` for those tests and source syntax checks. Run `make help` to list the commands.

For the Playwright UI tests, install Node.js and run the following from the workspace root:

```sh
npm ci
npx playwright install chromium --only-shell
make test-ui
```

The browser suite starts a local server on port 5189 and checks search, network and layer controls, failure recovery, responsive layouts, keyboard use and automated WCAG A/AA rules. It substitutes a minimal map style and search responses; it does not verify live map tiles, terrain, or the external search service. To additionally run the network-dependent desktop, mobile and landscape map smoke tests, use `NDT_LIVE_UI=1 npm run test:ui -- live.spec.cjs`. Automated accessibility checks do not replace testing with assistive technology.

To run the same UI suite in other engines, install them with `npx playwright install firefox webkit`, then use `NDT_BROWSER=firefox npm run test:ui` or `NDT_BROWSER=webkit npm run test:ui`.

See [the benchmark](../docs/BENCHMARK.md) for earlier visual and performance observations and their comparison limits.

## Project tasks and Overview

Select the original project name in the dropdown, then use **Tasks** to create tasks with editable IDs and names. Each task supports multiple named drive-test routes. Draw map waypoints and choose **Finish route**, or import LineString/MultiLineString GeoJSON (including Features and FeatureCollections); both automatically request a driving path along roads. Use **Fit to roads** on an existing route. **Save task** persists the draft in the root SQLite database. Start and End always use the first and last route coordinates. **View route** fits the path; **Remove route** edits the draft, and **Delete task** removes a saved task after confirmation.

**Project overview** opens a separate full-page screen with project context, sites and saved task summaries. **Back to map** returns to the map; **New task** and **Edit task** manage rows in the lower Overview table; **Map task editor** opens the geographic editor. Original project names, saved memberships and map boundaries are retained. Tasks also work in New York, where RF boundaries remain unavailable.

Limits: 100 tasks per project, unique 1–64 character task IDs using letters/digits/hyphens/underscores, 1–120 character names, 50 routes per task, 2–5,000 points per route and 10,000 points per project. Routes need two distinct WGS84 positions. GeoJSON import is limited to 2 MB, rejects unsupported geometry atomically and discards optional altitude. Solid blue routes are road fitted; dashed amber routes retain their original geometry and require review. Fitting contains no measured test results or live road-access verification. Save/discard before switching tasks; project switches retain drafts only within the current page session. A reload loses unsaved drafts. GET/PUT task endpoints have a 10-second client timeout; failed saves retain drafts. Whole-list saves do not detect multi-user conflicts.

Road fitting uses the [FOSSGIS OSRM service](https://routing.openstreetmap.de/about.html) by default. It sends guide coordinates to that service, with the source and privacy link shown in the editor. Set `NDT_ROUTING_URL` to an OSRM-compatible base URL to use a different service (for example, a local deployment). The adapter uses the driving route API, at most 100 ordered guide points, a 150 m snap radius and an 8-second upstream timeout; the browser timeout is 12 seconds. Dense imports keep endpoints and the largest bends as guide points, so fine trace details can change. The original path is kept if fitting fails; a failed refit keeps its previous fitted path. Stop road fitting and project switches cancel application of pending results. Save/discard after fitting. The server permits one upstream operation at a time, spaces requests by at least one second and caches its last 32 successful requests; import batches show progress and can be stopped. Public services provide no availability or road-access guarantee. Saved task data remains unchanged until Save task.

Task drive plans include **Drive speeds (km/h)**, driving distance, estimated duration and labeled WGS84 start/end latitude/longitude. Speeds are optional per-task case assumptions from 0.1 to 200 km/h; blank values remain unknown and prior single speeds become one case. **Save task** persists speed cases with the task. Duration uses summed geodesic route lengths divided by speed; it excludes traffic, stops, elevation and transfers between separate routes. Unfitted paths are marked provisional. The editor updates immediately after speed or path changes; Project Overview displays saved summaries. Task Start/End use the first/last route in listed order; per-route values appear under **Distance, duration & GPS**. These are planned positions and estimated time, not measured GPS observations or recorded driving time.

## SQLite task data and speed comparisons

Project Overview places task management in the full-width table below project context. Create/edit/save/cancel/delete task rows there; expand a route count for route and speed-case details. Use **Edit routes on map** to draw, import or refit shared geometry. Phone tables scroll horizontally while retaining task IDs.

Enter comma-separated **Drive speeds (km/h)** such as `20, 40, 60`. Up to 20 unique speeds from 0.1–200 km/h define test cases on the same routes. Blank means unknown; prior single-speed tasks become one case. Duration ranges and individual task/route case results use shared geometry, so adding speeds does not duplicate coordinates or request road routing again. These are constant-speed estimates, not recorded drive-test results.

The authoritative root `regions.sqlite3` now uses `drive_tasks`, `drive_routes`, `drive_route_points` and `drive_speed_cases`. Native views `drive_task_details`, `drive_route_details`, `drive_speed_case_details` and `drive_route_case_details` expose SQL-calculated distance, duration and GPS data. SQLite must support window and math functions. Application connections enable foreign keys and saves are atomic. Use the application API for validated data changes; whole-project writes have no concurrent-user conflict detection.

Existing `project_tasks` JSON lists migrate transactionally and remain in `project_tasks_legacy` as an inactive archive. A prior relational single-speed column is migrated to case rows. IDs, ordered geometry, guidance and extra task/route attributes are retained. Back up SQLite before upgrades; the archive is never imported again after migration.

```sql
SELECT region_id, project_id, task_id, name, distance_km, estimated_duration_s,
       start_latitude, start_longitude, end_latitude, end_longitude
FROM drive_task_details;

SELECT project_id, task_id, case_id, speed_kmh, estimated_duration_s
FROM drive_speed_case_details;

SELECT project_id, task_id, route_id, case_id, speed_kmh, distance_km, estimated_duration_s
FROM drive_route_case_details;
```

## Project use cases

Select a project and choose **USE CASES** in navigation or **Use case** in Project Overview: **Virtual Drive Test**, **Parameter A/B Test** or **AI-RAN Algo. Benchmark**. Choices save immediately, synchronize across both dropdowns and persist in `project_use_cases` in SQLite. **Uncategorized** clears the choice and is the initial state for existing projects. Each Toronto and New York project has its own category. Failed loads offer retry; failed saves restore the accepted choice. These categories label project purpose; they do not execute tests or benchmarks. Original project names, memberships and task data remain independent.
